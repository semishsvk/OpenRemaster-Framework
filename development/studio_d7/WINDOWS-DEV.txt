OpenRemaster Studio Windows DEV preview

Extract the ZIP into a user-writable folder and run OpenRemaster-Studio-DEV.exe.
Windows x64 and an installed Microsoft Edge WebView2 Runtime are required.
The runtime is available from https://developer.microsoft.com/microsoft-edge/webview2/.
Windows may show an unknown-publisher warning for this unsigned preview.

The archive is a portable development preview. Remove its extracted folder
to uninstall it. Application webview data may remain in the current user's
application data directory under dev.openremaster.studio-shadow.

Settings includes a Studio DEV releases panel. Check DEV releases makes an
explicit public GitHub API request, displays the release's source and CI status,
and opens release/download links in the default browser. Select a downloaded
ZIP to compare its local SHA-256 with GitHub metadata. File bytes stay local.

The default desktop target includes the UI and archived observations. Its
optional HomePC DEV worker integration requires a separate feature and local
commissioning. Studio queries compiled capabilities before enabling worker
controls. Worker-enabled builds persist the operation ID before submission,
restore status after restart, and show bounded stdout/stderr log tails and
artifact details. Active status refreshes never resubmit a build. Unknown
outcomes retain their operation ID for review.
A verified completed build or an explicitly acknowledged, diagnosed hold allows
a separate new submission. Review held operation requires a diagnostic note
and confirmation. The client compares the current evidence digest under the
existing queue/writer locks, preserves the logs and records a local resolution.
It never retries the acknowledged operation ID. Queued work, unknown imported
IDs and missing stopped-process evidence remain on hold.
Closing Studio does not cancel a submitted build: the existing worker owns it.
Worker integration uses the pinned active HomePC worker 06 and understands its
QUEUED/RUNNING states. Status reads do not issue execution receipts or produce
per-query IPC logs. Only submit performs native DEV receipt admission.
Archive build logs preserves compressed complete stdout/stderr, a checksum
manifest and an evidence digest. Originals and ledger records are retained.
Archives are limited to 64 entries and a 256 MiB storage budget; one operation's
logs are limited to 64 MiB. Capacity exhaustion requires an explicit export and
review; there is no automatic deletion of historical or unresolved evidence.
Only incomplete generated archive copies are reclaimed under the existing
writer locks after interruption; complete archives and original logs remain.
Intent and acknowledgment records are published atomically and exclusively.
Admission checks terminal ledger metadata without rehashing every old build;
inspecting an operation still performs the full worker evidence validation.
The HomePC queue builds its existing pinned Studio source snapshot. A checkout
is not silently substituted for that input. The portable CI build is compiled
from the Git source identified in its build metadata.
Before you build shows native support, worker health, Owner/writer admission,
Resource Governor reservation, GAME/LIGHT mode, Windows worker account and
source binding. Read-only diagnostics expire after 30 seconds. A healthy
worker alone cannot enable submission. The current worker 06 route has no
accepted adapter to the original ControlPlane grants, so its native submission
gate remains closed until that integration is independently commissioned.

Fresh attempts have their own saved identity. A typed not-admitted record can
be acknowledged only when it matches that saved attempt and confirms absence
of intent, queue, ledger and launch under the existing locks. Missing or
contradictory proof preserves HOLD. This never retries the rejected ID.
If recording proof was blocked by a busy writer or an interrupted client,
Refresh build status can expose Verify this attempt was not admitted for a
fresh saved attempt. This dedicated check never invokes submit or issues an
execution receipt. It requires fresh evidence and the original locks; imported
IDs without an attempt identity remain held. The backend also enforces the
matching attempt when acknowledging a not-admitted record.

Build logs includes paged full-file access, page search, error/warning filters
and optional live following every 10 seconds. Live output is labeled partial;
archived reads verify compressed and complete decompressed bytes. Export
complete diagnostic ZIP includes the retained manifest and compressed logs;
Studio verifies the complete downloaded ZIP before saving it. Exports count
against the existing archive storage budget. Diagnostic files may contain
local paths and compiler output; review them before sharing with anyone.
The public preview has production admission disabled.

Configured HomePC builds also provide a read-only LOCAL_DEV view of the
existing Host/Broker: host identity/heartbeat, recent jobs and knowledge
checkpoint state. It refreshes every five seconds and expires after ten.
The native adapter uses a pinned reader and Python, with an eight-second
timeout and 64 KiB response limit. No database, start, retry or lease command
is exposed to this panel. A committed build can have CHECKPOINT_PENDING;
checkpoint recovery never resubmits that build. Portable previews report
local status unavailable. The legacy admission controls remain separately
blocked; their historical production HOLD is not LOCAL_DEV build authority.

BUILD-INFO.json records the source commit, build time, feature, toolchain,
workflow run and executable digest. SHA256SUMS.txt covers every archive file
except SHA256SUMS.txt itself; the published archive digest covers the whole ZIP.
THIRD-PARTY-NOTICES.txt and dependency-inventory.json record dependency license
metadata and copied notice texts. Entries without a notice file are identified
for review. LICENSING-PROPOSAL.txt records the proposed MIT license.

Archived game comparison images are included from the public source tree.
Their distribution rights and the complete dependency notices require review
for SignPath admission. A successful build establishes technical provenance.

Privacy

The UI reads bundled snapshots and can request same-origin review endpoints
when the user activates the corresponding control. The default native target
registers no DEV worker command. The selected source has no application
analytics or crash-reporting integration. WebView2 is a separately installed
Microsoft runtime with its own behavior and privacy terms.
The release panel contacts api.github.com after an explicit release check.
GitHub receives the normal request metadata. Requests use no stored credentials.
https://docs.github.com/site-policy/privacy-policies/github-general-privacy-statement

The application displays paths, project evidence and build status locally.
The public package includes the snapshots already in its source revision.
Review the exact shipped data before a production or SignPath release.

Code signing policy

The source repository is maintained under the semishsvk account. The production
signing provider is pending. The maintainer, reviewer and
manual signing approver must be named and their repository/SignPath MFA
confirmed. Code review by Claude is recorded separately from account roles.
SignPath attribution and signing integration can be finalized after acceptance.
Every signing request will require manual approval by the named signing
approver. CI publishes unsigned DEV previews with their source provenance.

Source-only status v2 candidate (20 November 2026)

This source delta has no replacement native EXE or inherited GUI qualification.
The v2 read-only consumer distinguishes unresolved HOLD, known FAILED_SETTLED,
COMMITTED and UNKNOWN. Settled failures retain original HOLD, launch count,
disposition kind and receipt SHA-256. Settlement does not mean build success,
knowledge verification, retry permission or release acceptance.
V1 responses retain raw HOLD history; settlement counts remain unavailable.
The next native increment pins local-status-v2-pins.json independently of legacy
dispatch controls. Missing or changed pins and unsupported schemas fail closed.
No fallback to the historical v1 reader is automatic. The qualified gen1 EXE
and its recorded v1 inputs remain unchanged during the current assembly.
Source reviews and controls records apply only to their exact source revision.
They do not qualify a native EXE or grant build, GUI or payload cutover admission.
Native compilation and GUI qualification require the explicit common increment.
